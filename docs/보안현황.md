# 보안 현황 — 무엇이 되어 있고 무엇이 안 되어 있나

주장이 아니라 **실측**이다. 각 항목은 DB 에 물어보거나 코드를 열어 확인한 것이고,
자동 검증이 있는 것은 그 파일을 적어 뒀다.

갱신 2026-08-20 · 검증 `backend/tests/test_identity_security.py`, `test_db_schema.py`

---

## 1. 되어 있는 것

| 항목 | 상태 | 검증 |
|---|---|---|
| 비밀번호 해시 | PBKDF2-HMAC-SHA256 **600,000회**, 사용자별 16B 솔트, 32B 해시. 평문 없음 | `test_password_hashing_meets_current_guidance` |
| 반복수 이행 | 로그인 성공 시 옛 해시를 조용히 재해시 — 재설정 없이 넘어간다 | 실측 확인 |
| 아이디 존재 노출 | 없는 아이디에도 같은 시간을 쓴다(타이밍 차이 제거) | 코드 |
| 자격증명 격리 | 앱 역할은 `identity.user_credential` 을 **직접 못 읽는다.** 로그인 함수 하나만 실행 가능 | `test_app_role_cannot_read_credentials_directly` |
| 전량 덤프 차단 | 로그인 함수는 아이디당 **한 행**만 반환. `%`·빈값·인젝션 문자열로 안 샌다 | `test_login_function_does_not_leak_other_accounts` |
| 남의 비밀번호 변경 | 함수 안에서 차단 | `test_cannot_change_someone_elses_password` |
| 사용자 목록 | 컨텍스트 없으면 0명 — 전량 조회 불가 | `test_user_list_is_not_readable_wholesale` |
| 행 수준 보안 | 가계부·포트폴리오·계정 — 남의 행이 SELECT 결과에서 사라짐 | `test_row_level_security_hides_other_users_rows` |
| 실패 시 방향 | 사용자를 못 정하면 **아무것도 안 보이는 쪽**으로 실패 | `test_no_current_user_means_no_rows` |
| 감사기록 | append-only. 트리거 + 권한으로 이중 차단 | `test_audit_events_cannot_be_modified` |
| 앱 최소권한 | `app_rw` 로 동작. DDL 은 소유자만 | `session.py` |
| 문장 타임아웃 | `statement_timeout 30s`, `idle_in_transaction 60s` | `session.py` |

### RLS 를 켤 때 두 번 틀렸던 것 (기록)

1. **슈퍼유저는 RLS 를 통째로 우회한다.** `FORCE` 도 못 막는다. Docker 의
   `POSTGRES_USER` 가 슈퍼유저라 그 계정으로 붙는 한 정책은 장식이었다.
2. **커넥션 풀에서 `SET ROLE` 이 풀린다.** 접속 시점에 걸면 재사용될 때 풀려 두 번째
   요청부터 무력해진다. 반대로 앞 요청의 정체성이 다음 요청으로 새기도 한다.

→ 둘 다 **트랜잭션 안에서 `SET LOCAL`**(`bind_request_context`)로 해결. 켠 줄 알고
있어서 더 위험한 종류라, 검증이 없었으면 그대로 배포됐을 것이다.

## 2. 안 되어 있는 것 — 우선순위 순

### 2.1 계정이 두 곳에 있다 (높음)

DB 로 옮겼는데 `data/auth.json` 이 그대로 있고 **로그인은 아직 그 파일을 읽는다.**
노출면이 두 배이고, 두 사본이 어긋날 수도 있다.

→ 인증 경로를 `identity.credential_for_login` 으로 갈아 끼우고 파일을 지운다.
지금 안 한 이유는 되돌릴 길을 남겨 두는 중이라서다. **DB 전환이 안정되면 바로 할 것.**

### 2.2 민감 데이터가 평문이다 (높음, 단 전면 암호화는 답이 아니다)

```
가맹점명  '성일마크사', '갓텐익스프레스 스타필드하남점'
거래금액  27000.00
이메일    admin@test.local
연소득    40000000.00
```

**"전부 암호화"는 실제로 못 한다.** 가맹점명은 검색하고 금액은 합계·정렬해야 하는데,
컬럼을 암호화하면 그 기능이 통째로 죽는다. 이건 게으름이 아니라 트레이드오프다.

계층을 나눠야 한다.

| 데이터 | 수단 | 이유 |
|---|---|---|
| 가맹점명·금액 | 접근통제(RLS) + **저장소 암호화** | 검색·집계가 핵심 기능 |
| 이메일 | 컬럼 암호화 + 조회용 해시 인덱스 | 동등 비교만 하면 됨 |
| 연소득·자산 | 컬럼 암호화 검토 | 집계 대상이 아님 |
| 비밀번호 | 이미 해시 | 복원할 이유가 없음 |

저장소 암호화는 볼륨/디스크 단에서 한다 — Windows BitLocker, 운영은 RDS/Cloud SQL 의
저장 암호화. `pgcrypto` 는 설치 가능한 상태로 확인해 뒀다.

### 2.3 DB 연결이 평문이다 (외부 배포 시 치명적)

```
서버 SSL 켜짐: off / 이 연결 SSL: False
```

로컬 루프백이라 당장 위험은 낮지만, DB 가 다른 호스트로 가는 순간 자격증명과 전 데이터가
네트워크에 그대로 흐른다. → 운영에서는 `sslmode=verify-full` 필수.

### 2.4 비밀·키가 평문 파일에 있다

`backend/.env` 에 DB 비밀번호, IMAP 비밀번호, DART·Finnhub·네이버·ECOS 키가 평문이다.
git 에는 안 올라가지만 디스크에는 그대로다.

→ 외부 배포 시 환경변수 주입 또는 비밀 관리자(AWS Secrets Manager 등). 로컬 단독
사용이면 디스크 암호화로 갈음.

### 2.5 그 밖

- **백업 없음** — 암호화 이전에 백업 자체가 없다. `pg_dump` 정기 실행 + 그 산출물 암호화
- **HTTPS 미적용** — 외부 노출 시 필수
- **의존성 취약점 스캔 없음** — 인증을 잘 짜도 라이브러리로 뚫린다.
  `pip-audit` / OWASP Dependency-Check 를 CI 에
- **로그인 실패 잠금 없음** — 속도 제한(`rate_limit`)은 있으나 계정 잠금은 없음
